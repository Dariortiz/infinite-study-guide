Confidential-compute architecture map

First decide whether a hardware/vendor TCB is acceptable. Then choose isolation granularity and platform by the claims you can verify and the residual leakage you can tolerate.

When a TEE is the wrong primitive

Use a TEELow-latency general computation must be isolated from a privileged host, and relying parties accept hardware/firmware/vendor attestation plus side-channel and availability limits.
Use FHEThe evaluator should never receive plaintext even if hardware and firmware fail. Use the FHE guide; a TEE may still protect keys or accelerate trusted setup.
Use ZKAnyone must verify an output from public evidence rather than trust a vendor-signed quote. See the ZK guide.
Use PQCThe concern is quantum-safe KEMs/signatures and long-lived encrypted traffic. Attestation signatures and endorsement chains also need migration. See the PQC guide.
Use MPCSeveral organizations should jointly compute or hold a key without one hardware vendor becoming the trust anchor. See the MPC guide.
Use the chainYou need shared ordering, data availability, settlement, and independent history—not confidential execution alone. See the chain guide.
Use sessionsYou need authenticated channels, forward secrecy, ratchets, or group messaging. Attestation can authenticate a workload into a channel but does not replace the session guide.

Which TEE shape

Process enclaveSmall application boundary and strong host-OS adversary model; porting and enclave transitions are explicit. SGX-like designs expose page/cache/host interfaces sharply.
Confidential VMLift a full guest while excluding the hypervisor/cloud operator from private memory. Easier compatibility buys a larger guest TCB and difficult device/I/O boundaries.
Secure world / RealmPlatform firmware and device use cases on Arm. TrustZone and CCA Realms have different isolation and ownership models; do not merge them.
Nitro EnclavePurpose-built isolated child VM with no persistent storage/network and tight AWS KMS integration. AWS hardware/control-plane trust is explicit.
Confidential containerContainer UX atop a confidential VM, Kata guest, attestation agent, KBS, policy, registry, and orchestrator. The container abstraction does not shrink the underlying VM TCB.
Common mistake: accepting any valid quote. Verify nonce/channel binding, debug and migration flags, exact or signer measurement policy, full TCB/security version, endorsement validity/revocation, reference provenance, verifier identity, and what secret or authority the result unlocks.

Capstones and study loop

Attestation capstone

  1. Build a deterministic enclave/CVM image with no embedded secrets.
  2. Generate nonce-bound evidence and validate its certificate/endorsement chain.
  3. Appraise measurement, configuration, debug/migration, and TCB version.
  4. Bind an ephemeral channel key to evidence and release a scoped secret.
  5. Reject stale, replayed, debug, outdated, and unknown evidence.

Adversarial systems capstone

  1. Expose a minimal host API and enumerate every observable.
  2. Fuzz host return values, timing, interrupts, and network ordering.
  3. Demonstrate a rollback or clone and add an external freshness design.
  4. Measure transitions, memory, latency, throughput, and side-channel variance.
  5. Write patch, revocation, migration, outage, and key-destruction runbooks.

Weekly cadence

  • Watch: write the actual exclusion list.
  • Derive: trace one measurement or evidence signature.
  • Build: reproduce the attested artifact.
  • Break: page, replay, roll back, clone, or lie via host I/O.
  • Explain: name every TCB and fallback.

Minimum portfolio

  • Cross-platform TEE threat matrix.
  • Quote/report verifier with negative tests.
  • Attestation-gated key release.
  • Gramine, Nitro, or CVM deployment.
  • Host-interface fuzz report.
  • Rollback and side-channel analysis.

Exit criteria

Trust and architecture
You can state the asset, adversary, TCB, exclusions, isolation granularity, memory/I/O protection, availability limits, and vendor/supply-chain roots for SGX, SNP, TDX, CCA, and Nitro.
Attestation
You can map platform evidence to RATS, verify freshness and endorsement chains, distinguish evidence appraisal from relying-party policy, and bind results to key release or a channel.
Implementation security
You can minimize enclave/guest and host-call surfaces, reproduce measurements, fuzz untrusted I/O, reason about page/cache/transient leakage, and prevent or explicitly externalize rollback/cloning.
Operations
You can maintain reference values, TCB minimums, revocation and patch policy, verifier availability, migration rules, observability without secret leakage, and incident response.
Place in the seven
You can reject a TEE when the requirement is hardware-independent ciphertext compute, public proof, joint computation, consensus, or secure sessions. You can design hybrids without erasing each component’s distinct trust model.
