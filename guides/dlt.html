Choose your route

There is no single public course covering consensus, execution, data availability, light clients, and programmable accounts at implementation depth. Roughgarden supplies the distributed-systems spine; protocol talks and labs keep the route current.

~24 hours

Protocol engineer route

Complete every core unit and its labs. You will implement a toy chain, inspect Ethereum state, verify a proof against a finalized header, and threat-model a smart account.

~47 hours

Cryptography deep dive

Complete every unit, including FLP, selfish mining, PoS design variants, DAS probability, bridge failure modes, PBS/MEV, formal verification, and both capstones.

Build-first

Full-stack route

Take Modules 0–2, then 4–5 and 9. Build with Foundry or Hardhat, but return to Modules 3 and 6–8 before calling any deployment trust-minimized.

Architecture and settlement map

First decide whether decentralized ordering and settlement are necessary. Then choose the smallest architecture whose failure and exit assumptions you can actually operate.

When a chain is the wrong primitive

Use a databaseOne organization is an acceptable writer and ordinary access control, audit logs, backups, and signatures meet the threat model. A blockchain adds consensus cost without removing that trust.
Use FHEOne evaluator must compute on ciphertexts. Putting ciphertexts on-chain adds settlement/publication; it does not create private computation. See the FHE guide.
Use ZKYou need a short public argument for a statement, not replicated ordering. A validity rollup composes ZK with this guide. See the ZK guide.
Use PQCYour concern is quantum-safe signatures/KEMs. Replacing a chain’s signature scheme is a migration problem; consensus does not make ECDSA post-quantum. See the PQC guide.
Use MPCA known set of parties should jointly compute or control a key. Threshold wallets are MPC; publishing their transactions and ordering them is the chain. See the MPC guide.
Use a TEEYou accept a hardware/vendor TCB and need confidential low-latency execution. An attested sequencer is still a different trust model from consensus. Guide 6.
Use sessionsYou need channel authentication, forward secrecy, ratchets, or group messaging. A wallet signature and a finalized block do not protect a conversation transcript. Guide 7.

Which settlement architecture

PoW longest chainOpen leader election and probabilistic settlement under hash-power and network assumptions. Appropriate only when energy/external-cost and mining centralization trade-offs are acceptable.
BFT / PoSFast economic/deterministic finality with validator identities or stake, quorum assumptions, slashing, and weak-subjectivity/checkpoint requirements.
L1 executionMaximum direct composability and settlement assurance, paid for with scarce globally replicated execution and storage.
RollupOff-chain execution with L1 data and settlement. Inspect sequencer, forced inclusion, upgrade keys, proof/dispute maturity, and exit path.
Validium / alt-DACheaper data publication with an additional DA committee/network assumption. Validity proofs establish correctness, not availability.
Smart accountProgrammable validation, recovery, sponsorship, and bounded session permissions. Security moves from one key into account code, modules, bundlers, paymasters, and upgrade policy.
Common mistake: comparing TPS or fees while omitting hardware requirements, state growth, finality, reorg risk, sequencer/bridge/admin keys, DA retention, censorship resistance, and whether a user can independently verify and exit.

Capstones and study loop

Consensus capstone

  1. Implement signed transactions, authenticated state, blocks, and a deterministic state transition.
  2. Add a simulated network with delay, partitions, and Byzantine messages.
  3. Implement either heaviest-chain PoW or a four-validator BFT protocol.
  4. Measure safety/liveness across adversary and delay sweeps.
  5. Write exactly what “final” means and what state is recoverable after a reorg.

Settlement capstone

  1. Deploy a minimal rollup-like state commitment or smart-account policy system to a local chain.
  2. Provide inclusion/state proofs and an independently verified exit/action path.
  3. Model sequencer/admin/bundler/paymaster failures.
  4. Add pause, rate limits, revocation, and monitored invariants.
  5. Report trust assumptions, gas, latency, proof/data bytes, and recovery time.

Weekly cadence

  • Watch: identify the safety/liveness claim.
  • Derive: work one quorum or probability bound.
  • Build: inspect bytes and state transitions.
  • Break: partition, reorder, withhold, replay, upgrade.
  • Explain: give the user’s independent exit story.

Minimum portfolio

  • Toy consensus/state-machine simulator.
  • Merkle/state-proof verifier.
  • Foundry invariant and exploit report.
  • Rollup/bridge trust map.
  • Blob/DA sampling notebook.
  • Bounded smart-account policy with red-team tests.

Exit criteria

Consensus
You can state safety, liveness, validity, finality, synchrony, fault threshold, Sybil-resistance, fork-choice, and incentive assumptions without merging them.
Execution and security
You can trace a transaction through state transition and gas, write invariants and adversarial tests, inspect upgrade authority, and explain why consensus does not make contract logic correct.
Scaling and verification
You can separate execution, sequencing, proving/disputes, data availability, and settlement; verify state under a finalized root; and explain why validity does not imply availability.
Programmable accounts
You can trace ERC-4337, distinguish it from EIP-7702, and design agent permissions with deterministic scope, simulation, revocation, rate limits, monitoring, and human-controlled policy changes.
