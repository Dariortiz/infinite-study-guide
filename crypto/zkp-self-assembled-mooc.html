Choose your route

The balanced route is the intended course. The shorter route preserves the conceptual chain but reduces protocol variety; the deep route adds full implementations and alternate constructions.

~15 hours

Protocol literate

Watch the core units, but use only the Berkeley programming lecture for Module 2 and choose one of Groth16 or STARK 101 for a build. Best for reading papers and evaluating claims.

~24 hours

Balanced prover-builder

The recommended route: all core units plus the Berkeley lab, PLONKathon, STARK 101 notebooks, and one zkVM receipt. Never let the implementation trail the theory by more than one module.

~42 hours

Cryptography deep dive

Complete every unit, including MoonMath, alternative commitment schemes, lookups/authenticated data, folding updates, Halo2/Noir, and both capstones. Add conference extras only afterward.

Proof-system map

First decide whether you need an argument at all. Then choose a system by relation, setup, commitment backend, prover/verifier budget, recursion, and deployment target.

When a SNARK is the wrong primitive

Use ZKA verifier should accept a short proof that a witness exists for a public statement, without learning the witness. Integrity first; privacy of inputs is optional and must be designed.
Use FHESomeone must keep computing on ciphertexts and return ciphertexts. A proof that they did so is a composition with this guide, not a replacement for the FHE guide.
Use MPCSeveral parties hold inputs and will interact. Proving that an MPC transcript was honest is again composition. See the MPC guide.
Use the chainYou need fork choice, data availability, light clients, or sequencer economics. Module 7’s zkEVM/zkBridge units are the NP relation; consensus is guide 5.
Use a TEEThe product trusts attestation and an enclave, not a mathematical argument. That is guide 6. A TEE quote is not a SNARK.

Which proof stack

Groth16Very small proofs and fast pairing verification; circuit-specific trusted setup; mature Circom/snarkjs path. Strong when a stable circuit and cheap on-chain verification dominate.
PLONK / PlonkishFlexible arithmetization with custom gates and lookups. Usually universal/updatable setup with KZG or transparent IPA commitments; the concrete backend changes setup, proof, and recursion properties.
STARK / FRITransparent, hash-based, and plausibly post-quantum; naturally fits execution traces/AIR. Larger proofs and different verifier costs, but excellent prover scalability and recursion engineering.
Sum-check systemsMultilinear-polynomial route used by Spartan, GKR descendants, Jolt-like designs, and newer multilinear commitments. Attractive linear-time provers, but assumptions and concrete verifier work vary.
Folding / IVCIncrementally compress repeated computation by folding instances; Nova-like systems still need a commitment and often a final compression proof. Folding is a technique, not a complete drop-in SNARK.
zkVMA full stack: ISA, arithmetization, memory argument, continuations, proof backend, recursion, and receipt format. Easier application programming shifts complexity into the VM and prover.
Common mistake: “zero knowledge” does not automatically mean private inputs, succinct proofs, proof of knowledge, transparent setup, post-quantum security, a correct application, or a rollup. State each property and assumption separately.

Capstones and study loop

The videos supply instruction; these projects force the mathematical and implementation views to agree.

Protocol capstone

  1. Implement Schnorr identification over a small group.
  2. Add special-soundness extraction from two transcripts with the same commitment.
  3. Apply Fiat–Shamir with explicit domain separation and public-input binding.
  4. Simulate honest-verifier zero knowledge.
  5. Write down exactly which security claim changes in the random-oracle model.

Systems capstone

  1. Choose one statement: private eligibility, Merkle/lookup membership in an attested table, or verifiable program execution.
  2. Implement it in Circom/Noir/Halo2 or a zkVM and define public/private inputs.
  3. Generate, serialize, and verify proofs; add a verifier integration.
  4. Attempt malicious witnesses and malformed public inputs.
  5. Report constraints/trace rows, setup, proof size, proving/verification time, peak memory, and assumptions.
  6. Write why this is a SNARK rather than FHE, MPC, a TEE, or “just put it on a chain.”

Weekly cadence

  • Watch: pause before each challenge or reduction.
  • Derive: reconstruct one equation without notes.
  • Build: reproduce one protocol layer in code.
  • Break: search for an invalid witness or transcript.
  • Explain: give a five-minute summary with no slides.

Comparison artifact

  • Relation and arithmetization.
  • Commitment backend and assumptions.
  • Setup ceremony and toxic waste.
  • Proof size, prover/verifier cost, and memory.
  • Recursion, batching, and hardware fit.
  • Implementation maturity and audit surface.

Exit criteria

Definitions
You can define proof versus argument, completeness, soundness, knowledge soundness/extraction, zero knowledge/simulation, succinctness, non-interactivity, and the relevant setup models without merging them.
Mathematics
You can work over finite fields, interpolate polynomials, explain Schwartz–Zippel, run sum-check on a small example, and state what pairings, Merkle trees, codes, and FRI contribute.
Construction literacy
You can trace program → witness → arithmetization → IOP → commitment → Fiat–Shamir → proof; compare Groth16, Plonkish, and STARK-style systems; and explain recursion versus folding.
Implementation and security
You can generate and verify a proof, inspect public inputs and constraints, measure costs, create an adversarial witness test, and explain why successful proof generation does not establish that the intended statement was encoded.
Place in the seven
You can reject a SNARK when the job is ciphertext compute (FHE), interactive joint computation (MPC), fork choice or data availability (chain), or a hardware TCB (TEE). You can explain Merkle vs polynomial vs lookup authentication without turning this guide into a blockchain course. You do not treat zkML as a missing core module.
