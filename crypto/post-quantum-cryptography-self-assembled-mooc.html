Choose your route

The core path is intentionally broad: primary standards plus mathematical diversification and deployment. The shorter path is for architecture decisions; the deep path adds cryptanalysis and implementation internals.

~16 hours

Quantum-ready architect

Watch the overview, standards, scheme summaries, implementation warnings, and migration units. Understand interfaces and trade-offs without deriving every transform.

~28 hours

Balanced implementer

The recommended route: every core unit plus ML-KEM/ML-DSA vectors, a native OpenSSL lab, hybrid TLS, and one adversarial test suite.

~55 hours

Cryptography deep dive

Complete everything: lattice reduction, full NTTs, code-based specialization, Falcon/FN-DSA, formal security, physical attacks, and both capstones.

What the labels mean

Prerequisites: discrete mathematics, linear algebra, probability, algorithms, modular arithmetic, and introductory cryptography. C or Rust helps for constant-time work; Python is enough for toy schemes and vector runners. No quantum-physics course is required.
Stay in this guide: this guide is post-quantum primitives—assumptions, FIPS algorithms, vectors, constant time, and plugging them into existing APIs (TLS groups, SSH KEX, HPKE as a KEM wrapper). Do not wait here for FHE, SNARKs, MPC, consensus, enclaves, or a Signal/MLS state machine; those are the sibling guides.
Naming rule: final ML-KEM and ML-DSA are not wire-compatible aliases for every historical “Kyber” and “Dilithium” implementation. New work should use ML-KEM-512/768/1024, ML-DSA-44/65/87, and current standard identifiers—not Round-3 KATs, old OQS names, or draft TLS code points.

Algorithm and status map

First decide whether you need a post-quantum primitive. Then choose by function, assumptions, size, assurance, protocol support, and regulatory status.

When PQC is the wrong object

Use PQCLong-lived confidentiality, signatures, or key establishment must survive a cryptographically relevant quantum computer. Replace RSA/ECC (and hybrids) with standardized KEMs and signatures.
Use FHEThe problem is computing on ciphertexts, not replacing factoring. Lattices overlap; the product does not. See the FHE guide.
Use ZKYou need a public argument, not a quantum-safe KEM. STARKs are plausibly post-quantum; that does not make this a SNARK course. See the ZK guide.
Use MPCSeveral parties hold inputs. Threshold ML-DSA is composition with the MPC guide, not a FIPS 204 chapter.
Use a TEEAttestation and an enclave TCB. Guide 6. A confidential VM does not replace ML-KEM for harvest-now/decrypt-later traffic you already sent.
Use session cryptoRatchets, MLS groups, transcript state machines. Guide 7. This guide stops at KEMs, signatures, HPKE as a wrapper, and hybrid TLS/SSH negotiation.

Which standardized algorithm

ML-KEM · FIPS 203Final since August 2024. Primary NIST KEM; module-LWE; three parameter sets. Establishes a shared secret—it is not bulk encryption or authentication.
ML-DSA · FIPS 204Final. Primary NIST signature; module-LWE/module-SIS with Fiat–Shamir and aborts. Balanced general-purpose choice, with signatures much larger than ECDSA.
SLH-DSA · FIPS 205Final. Stateless hash-based signature and assumption-diverse backup. Conservative foundations; large signatures and slower signing.
FN-DSA · FIPS 206In development as of August 2026. Falcon-derived compact signatures using NTRU lattices and Gaussian/FFT sampling; difficult to implement and validate safely.
HQC · FIPS 207Selected code-based backup KEM; standard under development, final expected in 2027. Larger bandwidth than ML-KEM, valuable assumption diversity.
FrodoKEM · ISO 2026ISO-standardized unstructured-LWE KEM. Conservative lattice structure with significantly larger keys/ciphertexts; useful where diversification justifies cost.
LMS / XMSSStateful hash-based signatures. Appropriate for controlled signing appliances with robust monotonic state; catastrophic if one-time state is reused or rolled back.
Status is not assurance: standardized algorithm, conforming implementation, passing vectors, FIPS-approved algorithm, FIPS 140 validated module, secure protocol integration, and side-channel-resistant deployment are distinct claims.

Capstones and exit criteria

Implementation capstone

  1. Use native OpenSSL 3.5+ for ML-KEM-768 and ML-DSA-65.
  2. Run ACVP and adversarial vectors.
  3. Test exact parsing, contexts, randomness, rejection, and zeroization.
  4. Measure constant-time evidence and full-system cost.
  5. Cross-test another implementation and document every assurance boundary.

Migration capstone

  1. Choose a browser service, embedded fleet, update system, PKI, VPN, or messenger.
  2. Inventory cryptography and data/key lifetimes.
  3. Define hybrid and fallback policy.
  4. Test interoperability, fragmentation, downgrade, and rollback.
  5. Write staged rollout, observability, emergency replacement, and owner metrics.
  6. Mark what is a KEM/signature swap versus what belongs in the session-protocol guide (ratchets, groups, transcripts).

Weekly loop

  • Watch: separate construction from security claim.
  • Derive: reconstruct one equation or game.
  • Build: reproduce one artifact with pinned versions.
  • Break: mutate inputs, randomness, state, or control flow.
  • Explain: state assumptions and deployment limits aloud.

Minimum portfolio

  • Toy LWE PKE and failure experiment.
  • Naive versus NTT polynomial multiplication.
  • ML-KEM/ML-DSA vector runner.
  • Lamport reuse exploit.
  • Constant-time test report.
  • Hybrid TLS capture and migration CBOM.

Exit criteria

Threat and standards
You can explain Shor versus Grover, harvest-now/decrypt-later, KEM versus PKE, final versus selected standards, and why symmetric cryptography is affected differently.
Mathematics and schemes
You can connect SVP/SIS/LWE, distinguish plain/ring/module structure, trace ML-KEM and ML-DSA, build SLH-DSA from its components, and explain code-based diversification.
Implementation security
You can use final APIs and vectors, parse exact encodings, test rejection and contexts, evaluate randomness, inspect constant-time behavior, and describe physical/fault risks.
Deployment judgment
You can justify parameter and algorithm choices, distinguish prototyping from validation, verify hybrid negotiation/fallback, quantify size/latency costs, and produce a prioritized migration plan.
Place in the seven
You can reject “just use PQC” when the job is FHE, a SNARK, MPC, a chain, or a TEE. You can plug ML-KEM into TLS/SSH/HPKE without turning this course into Signal or MLS. You treat lattices in FHE and lattices in ML-KEM as related math with different products.
