Choose your route

The default route is intentionally broad. Use the filters above to isolate theory or implementation, but keep at least one video from each side in every study week.

What the labels mean

Every video in the seven modules carries one or more of these pills. Click a pill—or use the filter buttons at the top—to show only that kind of video. The conference extras at the end sit outside the route and are unlabeled.

coreOn the default route. Together these form the shortest path that still covers both the math and the implementation side.
theoryExplains why a construction works: lattices, LWE, noise, bootstrapping, scheme design.
buildShows or motivates working code—libraries, compilers, parameters, benchmarks. Each has an exercise attached.
optionalExtra depth or a second explanation of something already covered. Skip on a first pass without losing the thread.

Twenty of the twenty-six videos are core; the other six are optional, so a pill combination like core optional never appears. A handful of talks that both explain a construction and demo it carry three pills.

Prerequisites: comfort with linear algebra, modular arithmetic, basic probability, and one programming language. You do not need prior lattice cryptography. Rust is useful only for the TFHE-rs branch; Python is enough for the first implementation pass.
Stay in this guide: this guide is ciphertext compute—schemes, noise, compilers, parameters. Functional encryption is extras only (the output is in the clear). Do not wait here for proofs (guide 2), MPC (4), consensus (5), TEEs (6), or Signal (7).

Scheme and primitive chooser

First decide whether FHE is the right object. Only then choose a scheme by algebra and data layout—not by whichever library you installed first.

When FHE is the wrong primitive

Use FHEOne party should evaluate an agreed function on ciphertexts and return ciphertexts. The evaluator must not learn x or f(x). Typical: outsourced exact/approximate arithmetic with a single data owner.
Use MPCSeveral parties hold inputs and none of them should see the others’. Secret sharing, OT, and garbled circuits are usually cheaper than FHE when you can afford interaction. See the MPC guide.
Use ZKYou need a public argument that a computation was done correctly, not a ciphertext the server can keep evaluating. FHE + a SNARK is a composition, not a default. See the ZK guide.
Use a TEEThe product actually trusts a hardware TCB, attestation, and a sealed enclave or confidential GPU. That is guide 6, not an FHE optimization. FHE does not need Intel/AMD/NVIDIA to be honest.
Use FE / ABEA key should reveal f(x) in the clear and nothing else. That is not homomorphic evaluation. Definitions live in conference extras below; pairings/IBE details belong with ZK extras, not as extra FHE modules.

Which FHE scheme

BFV / BGVExact modular integer arithmetic, usually SIMD-packed. Good when exactness and modular semantics are natural; comparisons and arbitrary nonlinear functions remain awkward.
CKKSApproximate real/complex vector arithmetic. Usually the first choice for linear algebra and many ML inference workloads; precision, scale, rescaling, and polynomial approximations are part of program design.
TFHE / FHEWBoolean or fixed-width integer work with fast functional/programmable bootstrapping. Strong for comparisons, bitwise logic, and lookup tables; large vector arithmetic may favor CKKS/BFV/BGV.
Hybrid schemesSwitch schemes when a workload combines vectorized smooth arithmetic with a few non-smooth operations. OpenFHE, for example, supports CKKS↔FHEW/TFHE scheme switching, but conversion is not free.
Common mistake: “fully homomorphic” means arbitrary circuits are possible in principle. It does not mean every operation is practical, that the library chose secure parameters, or that FHE beats MPC, a TEE, or a proof for this product.

Capstone and study loop

The videos are the instruction; the prompts below turn each implementation video into deliberate practice.

Balanced capstone

  1. Choose a small model or scoring rule with a documented client/server threat model.
  2. Implement a cleartext baseline and define acceptable numerical error.
  3. Build one CKKS or exact-integer version and one TFHE-style version.
  4. Measure key sizes, ciphertext expansion, compile/keygen/evaluation latency, precision, and throughput.
  5. Explain which operations dominate and redesign one circuit to reduce depth or bootstraps.
  6. Document the security level and where every parameter came from.
  7. Write one page on why this workload is FHE rather than MPC, a TEE, or a SNARK—or admit that it is not.

One-week cadence per module

  • Watch: pause and predict the next construction or API step.
  • Reconstruct: redraw the key equations or type the demo without copying.
  • Break: exceed depth, use a bad scale, or run debug mode and observe failure/performance.
  • Explain: produce a five-minute verbal summary with no slides.
  • Connect: state how the math predicts the behavior you measured.

Exit criteria

Foundations
You can define correctness, compactness, semantic security, leveled FHE, and bootstrapping; explain LWE noise; and distinguish the main lattice problems without conflating them.
Scheme literacy
Given an operation graph and data type, you can justify BGV/BFV vs. CKKS vs. TFHE, estimate multiplicative depth, identify costly operations, and describe the packing strategy.
Implementation
You can run encrypted computation in a maintained library, validate against cleartext, measure error and latency, separate client/server artifacts, and avoid inventing parameters.
Systems judgment
You can explain what the compiler must lower and optimize, what the security estimator contributes, and why API success does not establish deployment security.
Place in the seven
You can reject FHE when several parties hold inputs (MPC), when you only need a public proof (ZK), when the product is a hardware TCB (TEE), or when a key must reveal f(x) in the clear (functional encryption). You do not treat those as missing FHE lectures.

Functional encryption — parent idea, not an FHE module

FHE evaluates f on ciphertexts and returns a ciphertext. Functional encryption issues a key for f and reveals f(x) in the clear. That is a different primitive. These talks are enough to see the distinction; they are not a substitute for pairings depth (ZK extras) or TEEs (guide 6).
